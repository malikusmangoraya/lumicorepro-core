# Lumicore Project Design Uniqueness

**Status:** Approved and implemented (2026-10-07)

## Purpose

Make websites generated by Lumicore feel specific to their product and brand,
and reduce repeated visual recipes across projects generated in the same
Lumicore workspace. This feature changes design selection and records its
decisions. It does not change quality-gate pass/fail behavior or scores.

## User and success criteria

The user asks Lumicore to generate a website and expects a design that is not a
relabelled copy of another Lumicore-generated site. The feature is successful
when:

- New projects select and apply a coherent, brand- and product-relevant final
  UI style and palette before code generation and post-build restyling.
- The signature compares the final UI style, palette, and available design
  decisions against existing readable project manifests, rather than relying
  on a different color alone.
- The selected decisions are saved in the generated project's existing
  `design-manifest.json` and can be reproduced or inspected later.
- Existing projects retain their current design when edited unless the user
  explicitly requests a redesign.
- User constraints, accessibility, responsive behavior, and product-specific
  usability take precedence over forced visual variation.
- Existing score fields, gate results, and pass/fail behavior remain unchanged.

## Current behavior

The main generation path creates decisions in
`ai-agent/agent/intelligence/design_decision_engine.py` and persists a subset
through `DesignManifestWriter` in
`ai-agent/agent/intelligence/design_manifest.py`. The manifest currently
records brand, visual density/motion/3D, typography, colors, spacing, components,
industry, references, and reproducibility metadata.

The separate `HyperUniqueSiteEngine` chooses from six palettes and six font
pairings, then returns a largely fixed navbar, hero, feature, pricing, and
footer recipe. It is not the normal orchestration path. The main generation
flow already has the correct decision and persistence boundaries, so this
feature extends those rather than adding a competing engine.

## Design signature

Each new project receives a structured, deterministic signature containing
available decisions in these dimensions:

- Brand personality and archetype.
- Visual direction and surface/card treatment.
- Page and section composition, including hero treatment.
- Typography pairing and hierarchy.
- Palette and semantic color roles.
- Final ProDesign UI style, selected from its supported style catalog.
- Image/illustration treatment.
- Motion vocabulary and 3D usage.
- Navigation and interaction patterns.

The signature must represent choices actually passed to generation, not just
descriptive metadata. Missing or unavailable choices remain unspecified rather
than being fabricated. The signature includes a stable digest/version so the
choice can be reproduced and the algorithm can evolve.

## Portfolio-aware selection

Before selecting a signature for a new project, read existing
`design-manifest.json` files beneath the configured
`GENERATED_PROJECTS_DIR`. Treat those manifests as read-only comparison input.
Ignore unreadable, malformed, or legacy manifests that lack comparable design
fields; do not let one bad file abort generation.

Prefer candidates that:

1. Satisfy explicit user brand/style constraints and industry needs.
2. Keep accessibility, responsive, performance, and reduced-motion
   constraints intact.
3. Differ from prior Lumicore project signatures across several dimensions.
4. Remain deterministic for the same prompt, project identity, and portfolio
   snapshot.

The final rendered UI style is selected from the existing ProDesign style
catalog. The resolved style palette is passed to the design planner and the
post-build restyler so the visible theme, design plan, and saved signature
agree. Explicit prompt color hints and measured screenshot colors are validated
as hex values and retained as palette overrides. An explicit named style,
reference-derived style, or analyzed screenshot style is not replaced merely
to reduce portfolio overlap.

Do not vary every dimension randomly or force 3D, animation, a particular
palette, or a fixed section list. Variation must be meaningful and coherent.
If the portfolio has no comparable manifests, use the current design decision
rules and record the resulting signature. If all candidates are constrained by
the user's explicit requirements, preserve those requirements and record the
overlap rather than silently overriding them.

No remote website scraping, global web-wide uniqueness claim, new database,
third-party API, or user-visible score is part of this feature.

## Existing-project behavior

When a generation or iteration targets an existing project with a valid design
manifest, load and preserve its signature by default. Apply only the requested
design changes and update the manifest with a new version/history entry using
existing manifest conventions where available. A request to "redesign" or
change a particular design dimension may replace those decisions; unrelated
approved choices remain stable.

## Integration boundaries

- Extend the design-decision layer to accept project identity, explicit user
  constraints, and a compact summary of prior signatures, then return selected
  signature fields with the existing decision.
- The orchestrator obtains the portfolio context from
  `GENERATED_PROJECTS_DIR`, applies the selected decisions before code
  generation, and persists the same applied decisions in the project manifest.
- The final `restyle_project` pass consumes the selected `ui_style` and safe
  `palette_override`; when no override is supplied, current restyle behavior
  is unchanged.
- Extend manifest read/write support for a versioned signature without
  removing or renaming current fields.
- Keep the standalone Hyper-Unique helper API backward compatible. The normal
  pipeline must no longer rely on its fixed generic recipe for uniqueness.
- Do not change gate names, `overall_score`, readiness flags, or pass/fail
  semantics.

## Failure and compatibility behavior

- Missing output directory means an empty comparison portfolio.
- Unreadable individual manifests are skipped; valid manifests still inform
  selection.
- Existing manifests without the new signature format remain readable and
  contribute only fields they actually contain.
- Portfolio scanning is bounded to generated project directories and
  `design-manifest.json`; do not recursively read source files or secrets.
- If portfolio analysis fails, continue with the existing deterministic
  design-decision behavior and report the comparison limitation in run
  provenance, without claiming cross-project comparison occurred.
- New behavior must be deterministic and must not mutate prior projects.

## Out of scope

- Changing quality scores, QA pass/fail logic, or release readiness rules.
- Replacing the design planner, visual critic, or browser QA.
- Guaranteeing uniqueness against every public website or design ever made.
- Changing project APIs, provider routing, model choice, or deployment.
- Rewriting existing project manifests in bulk.
- Forcing a fixed number of palettes, fonts, pages, animations, or 3D scenes.

## Validation criteria

- Unit tests show that signatures are stable for identical inputs and differ
  when meaningful design decisions differ.
- Portfolio selection avoids reusing the same multi-dimension signature when
  compatible alternatives exist.
- The selected UI style reaches the final restyler; explicit color/screenshot
  palette values reach its tokens and design plan.
- Explicit user constraints win when they conflict with portfolio novelty.
- Missing, malformed, legacy, and unreadable manifests do not crash selection
  and do not get modified.
- Existing-project iteration preserves unrequested design decisions and
  updates only requested dimensions.
- Orchestrator integration proves the selected signature reaches code
  generation and is written to the generated project manifest.
- Existing score/gate output contracts and standalone Hyper-Unique helper
  tests remain compatible.
- Run the focused tests first, then the complete `ai-agent/tests` suite when
  declared dependencies are available. If a dependency is unavailable, report
  the blocked collection modules and run all other test files in shards.
